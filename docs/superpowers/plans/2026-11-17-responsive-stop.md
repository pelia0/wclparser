# Responsive safe Stop

The user pressed Stop while the existing 32-worker process was overloaded. Status calls time out, the UI starts a new status request every second without waiting for the prior one, and the Stop button gives no immediate feedback. The supplied console log shows ordinary status access logs, one successful Stop followed by another Start, and Windows Proactor ConnectionResetError(10054) during connection teardown. Current heavy queue reads run synchronously on the application loop. Source fixes must preserve durable snapshot/write ownership and the user's manual server restart policy.

- [x] Pipeline: execute large catalogue selector/count reads outside the application loop with bounded ownership; cancellation freezes all worker admission immediately and initiates API/browser cancellation before waiting for any atomic writer. Existing finite normal drain behavior remains compatible. Preserve queued API/full snapshots and await active writers.
- [x] API: retain default synchronous Stop contract for existing callers, add optional `wait=false` that acknowledges Stop promptly with 202 without disk/DB statistics. Keep cleanup owned by the application, expose stopping state, reject competing jobs and observe background cleanup errors. Shared stop task remains idempotent and disconnect-safe.
- [x] UI: coalesce status polling, handle fetch failures, show immediate STOPPING/request state, disable conflicting controls during Stop, use optional asynchronous Stop on supported servers, preserve displayed counters and reject stale poll responses. Support old servers with clear waiting feedback. Bump asset version.
- [x] Barrier regressions for blocked reads/writers, repeated Stop, disconnected callers, polling coalescing, stale responses and HTTP errors. Full suite and independent review passed; publication is source-only. Do not forcibly terminate or restart the live server.
